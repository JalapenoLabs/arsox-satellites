# The workspace

Every thread owns one subtree of the workspace root, named for the thread:

```
/workspace
  |-- <thread-id>/
    |-- repos/
      |-- <repo-name>/
```

The root is `ARSOX_WORKSPACE_ROOT`, defaulting to `/workspace`. Mount it as a
named volume: nothing under it survives a container replacement otherwise, which
silently breaks thread resumption.

Thread ids are UUIDv7 generated by the satellite and never accepted from a
client, because they become filesystem paths. The check that enforces that lives
in `workspace::thread_directory` and cannot fire today. It stays because the day
something else supplies an id, a traversal there reaches the whole volume.

Repo directory names **do** come from the client, through `Repo.name`, and are
checked the same way. An undeclared name is derived from the URL: the last
segment, minus any `.git`, for both HTTPS and SSH remotes.

## Provisioning runs once, in the background

Provisioning happens at thread creation and never again. Later turns inherit the
clones.

A thread that declares repos opens `PROVISIONING`. The create request returns
immediately and the cloning runs behind it. Cloning three repos and running a
`yarn install` in each is minutes of work, and holding the HTTP connection open
for it would make the satellite's most ordinary call its slowest.

**The guarantee that no turn runs in a half-cloned workspace lives in the claim
query, not in the runner.** `claim_next_turn` refuses to hand out work from a
thread that is `PROVISIONING` or `PAUSED`, so a turn submitted a millisecond
after the create simply waits, and the rule holds even if a second runner ever
appears. Turns may be queued freely while a thread provisions.

The collector will not sweep a `PROVISIONING` thread either. A clone in progress
is work in flight, and removing the subtree underneath it would leave git
writing into a directory that no longer exists.

A thread that declares no repos has nothing to provision and opens `IDLE`,
exactly as it did before provisioning existed.

## Where a thread lands

| Outcome | Thread state | Why |
|---|---|---|
| Nothing to do, or everything worked | `IDLE` | The queue starts moving. |
| A setup command exited nonzero | `IDLE` | The checkout is there. Something in it is missing. |
| A repo would not clone | `PAUSED` | The thread cannot work in this workspace. |

`PAUSED` rather than destroyed, because a parked thread keeps its queue and its
settings. An operator who fixes the remote resumes the thread onto the turns
that were already waiting. Destroying it would throw away the only thing the
caller still holds.

## Failures are incidents, not errors

By the time provisioning fails, the create request answered long ago. There is
nobody to return an error to, which is exactly the situation incidents exist
for. Every failure is written to the database and emitted on the thread's event
stream.

| Code | Disposition | Retryable | Ends provisioning |
|---|---|---|---|
| `REPO_CLONE_FAILED` | `fatal` | yes | yes |
| `REPO_SETUP_FAILED` | `degraded` | no | no |

A clone fails for reasons that pass: a rate limit, a remote restarting, a name
that has not propagated. A setup command exits the same way every time.

Incidents carry the evidence rather than a conclusion: the repo, the command,
its exit code, and its captured output, all in `details`. Output is truncated
from the front at 16 KiB, keeping the tail, because the error is at the end and
the preamble is a package list.

A repo whose clone fails ends provisioning immediately. The repos below it are
never attempted, because racing them only to throw the results away buys nothing.

## Setup commands

`Repo.setup_commands` runs after the clone, with the working directory at the
repo root, through a shell. They are written as shell text, so
`yarn generate && yarn build` means what a shell says it means.

The separator is the schedule, and it is the same syntax checkers use:

- **Newlines** run in parallel and do not fail fast.
- **Semicolons** are barriers. Nothing below a barrier starts until everything
  above it has succeeded.

A command that never ran because a barrier above it failed is reported as
skipped rather than omitted, and gets its own `REPO_SETUP_FAILED` incident
saying so. "Not run" and "found nothing" are different facts.

## Credentials are lent, never left behind

A clone needs a credential for as long as it runs, and everything that makes one
convenient also makes it persistent. The three obvious places are all wrong:

- **In the URL.** `git clone` writes the remote into the new repository's
  `.git/config`, so an embedded token sits on disk for the life of the
  workspace, readable by every agent working in it.
- **In argv.** Every process on the box can read another's command line.
- **In config.** `git clone -c key=value` persists into the clone. Only
  `git -c key=value clone` is scoped to the invocation, and the difference is a
  single token's position on the command line.

So:

**A personal access token** travels in the git process's environment and is read
from there by a credential helper passed with `git -c`. The helper answers
`get` and stays silent for `store` and `erase`, which keeps the token out of any
on-disk credential cache. `GIT_CONFIG_PARAMETERS` and the environment are both
inherited, so submodule clones authenticate without anything being recorded.

**An SSH private key** is written to a private temporary directory, created
`0700` with the key at `0600` as it is opened, because ssh refuses a key with
loose permissions and a chmod after the write leaves a window where they are.
The directory is removed when the clone returns, however it returned.
`GIT_SSH_COMMAND` points ssh at it with `IdentitiesOnly=yes`, so an agent key
loaded on the host cannot authenticate as somebody else, and `BatchMode=yes`,
because a satellite has no terminal to answer a prompt.

Host keys are accepted on first use into a `known_hosts` that lives and dies
with that directory. The contract carries no host key field to pin against, and
refusing every unknown host would mean no SSH remote ever clones.

`GIT_TERMINAL_PROMPT=0` is set on every invocation. Without it a remote that
wants a credential blocks on a terminal that is not there, and the satellite has
no way to notice.

Every spawned process, git and setup commands alike, goes through
`harness::spawn::scrubbed_command`, which strips every `ARSOX_*` variable and
every provider credential. The same scrub a harness gets, for the same reason.

Anything reaching tracing or an incident is redacted twice over: a credential
somebody wrote into a URL themselves is masked by pattern, and a token Arsox was
given is masked by value.

## Roadmap

- The agents repo, cloned once into `.agents` and materialized into `.claude`
  and `.codex`.
- `AGENTS.md` assembly, and the `CLAUDE.md` and `CODEX.md` pointers.
- Issue and ticket prefetch into `issues/`.
- Per-member worktrees under `members/`, cut from the single clone in `repos/`.
- Per-thread disk quotas, and `workspace_bytes` on a thread summary.
- A bound on how long provisioning may take. Today `GIT_TERMINAL_PROMPT=0`
  removes the common hang, and git's own network timeouts cover the rest, but a
  wedged clone holds its thread against collection indefinitely.
